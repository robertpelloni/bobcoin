# Project Memory & Architecture Summary

## 1. High-Level Vision & Architecture
The project, initially named "Bobcoin" and currently rebranding to **"Lattice Arcade"**, is a decentralized, gamified Sovereign Network built on an **Asynchronous Block Lattice** architecture. It abandons traditional monolithic global chains in favor of a Directed Acyclic Graph (DAG) of account chains, aiming for high throughput and native game economy mechanics (like Demurrage).

The architecture consists of a highly decoupled monorepo containing multiple microservices:
- **Frontend (`frontend/`)**: A React/Vite/PWA application that acts as the primary user portal, dashboard, and web-based gaming client. It leverages WebGL (via `react-three-fiber`) for chain topology visualization and the Web Audio API for custom synthesis.
- **Go Lattice (`go-lattice/`)**: The canonical, high-performance Go port of the core Block Lattice consensus engine, using SQLite for persistence. It replaces the legacy JavaScript `bobcoin-consensus`.
- **Go Microservices (`go-game-server/`, `go-supertorrent/`)**: These are the newly canonized core services. 
  - `go-game-server` handles system wallet orchestration, market endpoints, WebSocket matchmaking, FHE oracle bridging, and ZK proof verification orchestration.
  - `go-supertorrent` handles WebTorrent integration, Data Anchoring via Solana, and Succinct Proof of Random Access (SPoRA) consensus mechanics.
  - *Note: Their Node.js predecessors (`game-server/`, `supertorrent/`) are officially deprecated to consolidate performance under the Go stack.*
- **Zero-Knowledge SP1 Infrastructure (`proof-of-play/`)**: A Rust-based workspace that utilizes Succinct's SP1 zkVM. It contains the core RISC-V `program` for "Proof of Play" execution and a `script` wrapper that exposes a `warp` API proxy for the Go backend to consume.
- **Rust Lattice (`rust-lattice/`)**: Newly bootstrapped in Phase V to research migrating the block structure and proof parsing logic out of Go and into Rust for native "In-Protocol Proving."

## 2. Core Mechanics & Consensus Patterns
- **Proof-of-Useful-Stake (PoUS) / SPoRA**: Mining requires nodes to seed public data via Bobtorrent. Nodes must provide Succinct Proofs of Random Access to validate block creation.
- **Proof-of-Play (PoP)**: Token generation (minting) requires verifiable proof of human skill, validated by SP1 ZK circuits to prevent botting or macro scripting (with fallback "AI Oracle" variance analysis).
- **Fully Homomorphic Encryption (FHE)**: Used for privacy-preserving gameplay calculation, executed via Microsoft SEAL (`node-seal`) without revealing raw scores to the server.
- **Consensus Parity Validation**: The project strictly enforces 1:1 mathematical and semantic parity between the JS and Go consensus engines. This is maintained via extensive shared fixture fragments and scenario catalogs (`testing/parity-scenarios.json`) that are executed identically across both language test suites.

## 3. The "Autopilot Workflow Protocol"

- **Global Documentation Maintenance**: Agents must aggressively track project state across a suite of Markdown files (`ROADMAP.md`, `TODO.md`, `VISION.md`, `HANDOFF.md`, `IDEAS.md`, `CHANGELOG.md`, `VERSION.md`).
- **Single Source of Truth**: The global version string is driven entirely by `VERSION.md`. Version bumps must be synchronized and explicitly mentioned in commit messages.
- **Module Dashboards**: All active internal modules, tools, and nested external submodules (e.g., `research/forest`, `research/solana`) are tracked visibly in `docs/modules/INDEX.md` and visually in the UI (`frontend/src/pages/Architecture.jsx`).
- **Session Continuity**: Every session explicitly summarizes progress, remaining gaps, and next immediate steps in a massive `HANDOFF.md` to ensure frictionless context transfer between distinct LLM agents.

## 4. Current State & Future Roadmap (Phase V)

- **Focus Shifts**: Moving from a dedicated web-game backend to a Universal Achievement Layer. This involves building out endpoints like `/sdk/v1/submit-trace` for cross-game engines (Unity/Unreal).

# Project Memory & Architecture Summary

## 1. High-Level Vision & Architecture
The project, initially named "Bobcoin" and currently rebranding to **"Lattice Arcade"**, is a decentralized, gamified Sovereign Network built on an **Asynchronous Block Lattice** architecture. It abandons traditional monolithic global chains in favor of a Directed Acyclic Graph (DAG) of account chains, aiming for high throughput and native game economy mechanics (like Demurrage).

The architecture consists of a highly decoupled monorepo containing multiple microservices:
- **Frontend (`frontend/`)**: A React/Vite/PWA application that acts as the primary user portal, dashboard, and web-based gaming client. It leverages WebGL (via `react-three-fiber`) for chain topology visualization and the Web Audio API for custom synthesis.
- **Go Lattice (`go-lattice/`)**: The canonical, high-performance Go port of the core Block Lattice consensus engine, using SQLite for persistence. It replaces the legacy JavaScript `bobcoin-consensus`.
- **Go Microservices (`go-game-server/`, `go-supertorrent/`)**: These are the newly canonized core services. 
  - `go-game-server` handles system wallet orchestration, market endpoints, WebSocket matchmaking, FHE oracle bridging, and ZK proof verification orchestration.
  - `go-supertorrent` handles WebTorrent integration, Data Anchoring via Solana, and Succinct Proof of Random Access (SPoRA) consensus mechanics.
  - *Note: Their Node.js predecessors (`game-server/`, `supertorrent/`) are officially deprecated to consolidate performance under the Go stack.*
- **Zero-Knowledge SP1 Infrastructure (`proof-of-play/`)**: A Rust-based workspace that utilizes Succinct's SP1 zkVM. It contains the core RISC-V `program` for "Proof of Play" execution and a `script` wrapper that exposes a `warp` API proxy for the Go backend to consume.
- **Rust Lattice (`rust-lattice/`)**: Newly bootstrapped in Phase V to research migrating the block structure and proof parsing logic out of Go and into Rust for native "In-Protocol Proving."

## 2. Core Mechanics & Consensus Patterns
- **Proof-of-Useful-Stake (PoUS) / SPoRA**: Mining requires nodes to seed public data via Bobtorrent. Nodes must provide Succinct Proofs of Random Access to validate block creation.
- **Proof-of-Play (PoP)**: Token generation (minting) requires verifiable proof of human skill, validated by SP1 ZK circuits to prevent botting or macro scripting (with fallback "AI Oracle" variance analysis).
- **Fully Homomorphic Encryption (FHE)**: Used for privacy-preserving gameplay calculation, executed via Microsoft SEAL (`node-seal`) without revealing raw scores to the server.
- **Consensus Parity Validation**: The project strictly enforces 1:1 mathematical and semantic parity between the JS and Go consensus engines. This is maintained via extensive shared fixture fragments and scenario catalogs (`testing/parity-scenarios.json`) that are executed identically across both language test suites.
